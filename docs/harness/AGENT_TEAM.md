# 에이전트 팀

Toris Studio를 개발할 때 쓰는 에이전트의 역할, 모델, 넘겨주는 순서를 정합니다. 완료 판정 장치는 [하네스 엔지니어링](README.md)에 있습니다.

앱 안 Agent 탭의 Supervisor·Expert·QA는 제품 기능이고 이 문서의 대상이 아닙니다. [Agent 안내](../AGENT.md)를 보세요.

## 역할과 모델

| 역할 | 모델 | effort | 하는 일 | 고칠 수 있는 것 |
|---|---|---|---|---|
| 기획·피드백 (코디네이터) | Fable 5.2 `claude-fable-5-2` | 세션 설정 | 요청 해석, 작업 지시문 작성, 제안 검토, 결과 검수, 사용자 보고 | `docs/`와 작업 지시문. 제품 코드는 작업자에게 맡깁니다 |
| 구현 | Opus 5.5 `claude-opus-5-5` | high | 조사 → 제안 → 승인 뒤 구현, 테스트와 변형 추가 | 지시문에 적힌 범위 |
| 디자인 | Opus 5.5 `claude-opus-5-5` | high | 새 화면·바뀐 화면의 배치·문구·상태(빈 화면, 진행, 오류) 검토와 수정 | `desktop/src/**`의 화면과 CSS |
| QA | Opus 5.5 `claude-opus-5-5` | high | 구현자와 독립으로 검증하고 증거 수준을 구분해 판정 | 테스트와 변형. 제품 코드 결함은 구현자에게 돌려보냅니다 |

## 실행 (Orca)

코디네이터 세션에서 작업자를 띄웁니다.

```sh
orca orchestration worker-start \
  --spec-file <작업 지시문> --task-title "<제목>" \
  --worktree current --agent claude --model claude-opus-5-5 --effort high
```

- 작업자가 끝나면 Orca가 코디네이터를 깨웁니다. 상태를 반복 조회하지 않습니다.
- 끝난 작업자에게 `orca orchestration send --to dispatch:<dispatch_id> --subject "<주제>" --body "<내용>"`을 보내면 그 작업자가 조사한 맥락을 유지한 채 후속 작업을 받습니다. 제안을 승인하고 구현을 맡길 때 이 방식을 씁니다.
- 작업자의 질문(`ask`)에는 `orca orchestration reply --id <message_id> --body "<답>"`으로 답합니다. 지시문이나 사용자 지시로 답할 수 없으면 사용자에게 먼저 묻습니다.

## 흐름

```text
1 조사·제안 (구현 작업자, 읽기 전용, 여럿 동시에)
        ↓ worker_done: 근거와 제안
2 기획 검토 (코디네이터) ── 사용자 결정이 필요한 것은 사용자에게
        ↓ send: 승인한 범위와 피드백
3 구현 (구현 작업자, 한 번에 하나)
        ↓
4 디자인 (디자인 작업자)
        ↓
5 QA (QA 작업자) ── 실패하면 3으로
        ↓
6 보고 (코디네이터): 작업별 결과, 증거, 남은 문제
```

## 동시에 돌려도 되는 것

| 작업 | 같은 작업 폴더에서 동시에 |
|---|---|
| 읽기 전용 조사·제안 | 가능 |
| 문서만 고치는 작업 | 가능 |
| 제품 코드 수정 | 한 번에 하나 |
| Rust만 고치는 작업과 화면(TS·CSS)만 고치는 작업 | 가능. 고치는 파일이 겹치지 않고, 서로 상대 쪽을 빌드하는 명령을 돌리지 않을 때만 |
| `pnpm verify`, `harness-check`, Rust를 빌드하는 화면 검증 | 한 번에 하나. 다른 수정 작업이 없을 때만 |
| 변형 검사 | 한 번에 하나. 잠금이 있으면 기다립니다 |

제품 코드 수정을 동시에 하지 않는 이유는 세 가지입니다. 변형 검사가 실행 중에 소스 파일을 바꿔 씁니다. Rust는 크레이트 하나라서 한 작업자의 고치다 만 코드가 다른 작업자의 `cargo test`를 깨뜨립니다. `pnpm verify`는 작업 폴더 전체를 봅니다.

수정 작업을 꼭 동시에 해야 하면 작업자마다 별도 작업 폴더(`--worktree new-child --name <이름>`)를 줍니다. 새 작업 폴더에는 Git이 무시하는 런타임 자료(번들 FFmpeg, 글꼴, 에이전트 런타임 번들)가 없으니 준비 단계를 지시문에 넣습니다.

## 작업 지시문에 넣을 것

작업자는 지시문만 보고 일합니다. 다음을 모두 적습니다.

- **대상**: 저장소 경로와 먼저 읽을 문서
- **배경**: 사용자 요청과 코디네이터가 이미 확인한 사실
- **바꿀 것 또는 산출물**
- **제약**: `AGENTS.md`의 설계 원칙 중 이 작업에 걸리는 것, 하지 말 것
- **고쳐도 되는 파일**
- **완료 증거**: 통과해야 할 명령과 추가할 테스트·변형
- **실패 처리**: 0이 아닌 종료가 작업 실패인지, 그 출력이 산출물인지

## 단계 통과 조건

| 넘어가는 단계 | 조건 |
|---|---|
| 제안 → 구현 | 코디네이터가 범위를 승인. 외부 계정, 비용, 서버 운영, 게시가 걸린 선택은 사용자가 결정 |
| 구현 → 디자인·QA | 바꾼 기능의 `verify` 명령과 `pnpm verify` 통과. 새 파일의 소유 기능 지정 |
| QA → 완료 | `pnpm verify:full` 통과, 새 변형이 모두 `killed`, 증거 수준 표기 |
| 완료 → 커밋·푸시·게시·배포 | 사용자가 요청했을 때만 |

## 역할별 지시

지시문 앞에 붙여 씁니다.

**구현.** 실패하는 테스트를 먼저 쓰고 실패를 확인한 뒤 구현합니다. 새 동작마다 변형을 추가하고 `killed`를 확인합니다. 지시문 밖의 파일은 고치지 않고, 필요하면 코디네이터에게 묻습니다. 보고에는 바꾼 파일, 실행한 명령과 결과, 실행하지 못한 검증을 적습니다.

**디자인.** 기존 화면의 구성 요소와 CSS 변수를 먼저 씁니다. 빈 화면, 진행 중, 오류, 값이 긴 경우를 모두 확인합니다. 820px과 1380px 폭에서 넘침이 없는지 화면 검증 스크립트로 확인합니다. 화면 문구는 한국어로, 사용자가 다음에 할 일을 알 수 있게 씁니다. 동작을 바꾸지 않습니다.

**QA.** 구현자의 보고를 믿지 않고 직접 실행합니다. 지시문의 요구 사항을 하나씩 테스트·화면·렌더 결과에 대응시키고, 대응하는 증거가 없는 요구 사항을 보고합니다. 새 변형을 직접 돌려 `killed`를 확인합니다. 제품 코드의 결함은 고치지 않고 재현 방법과 함께 돌려보냅니다. 판정마다 증거 수준(단위 테스트, 고정 응답 UI 검사, 실제 렌더, 실제 외부 계정)을 적습니다.
