# Reason Network 연결

Toris Studio의 **Agent → Reason Network**에서 외부 에이전트와 메시지를 주고받고, 받은 영상 요청을 기존 영상 제작 작업으로 가져온다. 디자인·기획·개발·음향·배포는 **단계별 작업 맡기기**로 연결된 에이전트(Claude·Codex·피클·Muse·Grok Bot·OpenAI Dots 등)에게 차례로 넘기고, 영상 제작은 Studio의 기획·스토리보드 승인·로컬 생성·QA·게시 초안 흐름을 사용한다.

## 시작하기

1. 이 컴퓨터에서 [Reason Network 공식 안내](https://reasonmachines.com/network)에 따라 설치와 네트워크 참가를 완료한다. 터미널의 `reason network`로 연결을 확인한다.
2. 개발 중인 Studio는 `pnpm desktop:dev`로 실행한다. **Agent** 탭에서 **연결·받은 요청 확인**을 누른다.
3. 연결되면 **이 Studio 주소**를 복사한다. 주소는 Reason이 반환한 정확한 `사람/세션@컴퓨터` 주소다. 예시 문자열이나 내부 세션 UUID를 대신 사용하지 않는다.
4. 피클·Muse·Grok Bot·OpenAI Dots의 Reason 커넥터도 같은 네트워크에 연결한다. Studio는 이 에이전트들을 종류별로 구분하지 않으며, 네트워크에 접속해 **연결된 에이전트** 목록에 나타난 세션이면 무엇이든 단계 담당자로 고를 수 있다. 원격 MCP 주소는 `https://mcp.reasonmachines.com/mcp`이며, 로그인과 연결 절차는 [공식 문서](https://docs.reasonmachines.com/docs/network)를 따른다.
5. 외부 AI에게 복사한 Studio 주소로 메시지를 보내도록 요청한 뒤 Studio에서 받은 요청을 확인한다.

설치, 로그인, 새로운 네트워크 가입은 Studio가 자동으로 실행하지 않는다. Reason의 기존 로그인과 네트워크 설정을 이용하며 Studio의 화면에 Reason 토큰을 입력하지 않는다. 연결 목록·받은 요청은 탭 활성화 또는 확인 버튼으로 갱신한다.

## 앱 프로젝트: 경로 하나로 기획 → 디자인 → 구현

**Agent → Reason Network → 앱 프로젝트**에서 프로젝트 경로를 넣으면 그 폴더를 대상으로 기획·디자인·앱 개발을 이어서 진행한다.

1. **프로젝트 경로**에 `~/projects/my-app` 또는 `/Users/…/my-app` 같은 전체 경로를 넣고 **프로젝트 열기**를 누른다.
2. 네이티브 계층이 경로를 실제 폴더로 해석하고(`~/` 확장, `..`·심볼릭 링크 정리) 아래 "개발 에이전트 실행"과 같은 폴더 규칙으로 검사한 뒤, 폴더·브랜치·세션 이름·모델을 보여 주는 **OS 확인 창**을 띄운다. **실행**을 눌러야 그 폴더에서 구현 에이전트가 시작된다. 같은 폴더에서 Studio가 띄운 Claude 세션이 이미 실행 중이면 확인 창 없이 그 세션을 이어서 쓴다.
3. 구현 에이전트는 `reason network serve claude`로 실행한 Claude Code이며, 모델은 **Claude Opus 5.5 · effort medium**으로 고정한다(아래 "구현 모델 고정").
4. **만들고 싶은 것**을 쓰고 단계 담당을 확인한 뒤 **프로젝트 파이프라인 만들기**를 누른다. 연결된 에이전트 목록에 Muse·OpenAI Dots가 있으면 각각 기획 초안·기획 확정 담당으로 미리 골라 두며, 다른 에이전트로 바꿀 수 있다.

| 단계 | 기본 담당 | 하는 일 |
| --- | --- | --- |
| 기획 초안 | Muse | 프로젝트 현황과 브리프로 목표 사용자, 핵심 기능과 우선순위, 화면 흐름, 데이터·연동, 범위 밖, 열린 질문 |
| 기획 확정 | OpenAI Dots | 초안을 검토·보완해 수용 기준, 화면별 요소, 데이터 모델, 구현 순서, 검증 방법이 있는 최종 명세 |
| 디자인 | 사용자가 선택(건너뛰기 가능) | 색·서체·간격 토큰, 화면별 레이아웃과 컴포넌트, 빈 화면·로딩·오류 상태, 에셋 목록 |
| 개발 | 이 프로젝트의 구현 에이전트(고정) | 그 폴더에서 명세와 디자인대로 구현하고 바꾼 파일, 실제 실행한 빌드·테스트 결과, 남은 일을 답장 |

동작 원칙:

- 각 단계 요청은 아래 "단계별 작업 맡기기"와 같은 방식으로 보낸다. 요청 전문을 확인하고 **승인하고 보내기**를 눌러야 전송되며, 앞 단계 답장은 인용으로만 이어진다.
- 기획·디자인 요청에는 Studio가 폴더에서 직접 읽은 **프로젝트 현황**이 인용으로 들어간다: 감지한 구성(package.json, pubspec.yaml, Cargo.toml, Gradle, Xcode 등), 숨김 항목과 `node_modules`·빌드 폴더를 뺀 최상위 항목 48개까지, package.json의 이름·scripts·의존성 이름, README 앞부분 2 KiB. 전체 6 KiB 이하이며 일반 파일만 읽고 심볼릭 링크는 따라가지 않는다. 원격 에이전트에게 전송되므로 보내기 전에 전문을 확인한다.
- 기획·디자인 요청은 문서로만 답하고 프로젝트 파일을 수정하지 말라고 명시한다. 개발 요청은 그 폴더 안에서만 작업하라고 명시한다. 모두 커밋·배포·외부 게시·결제를 하지 말라고 요청한다(상대 에이전트에 대한 요청이며 강제 수단은 아니다).
- 개발 단계의 담당은 그 프로젝트의 구현 에이전트 세션 이름과 일치하는 주소만 허용한다. 생성·담당 변경·저장 기록 불러오기에서 모두 네이티브 계층이 검사한다. 개발 단계는 건너뛸 수 없으며, 필요 없으면 파이프라인을 취소한다.
- 화면은 실행 중인 세션의 ID만 보낸다. 폴더·브랜치·현황은 네이티브 계층이 그 세션에서 읽어 파이프라인에 저장하므로 화면이 폴더를 바꿀 수 없다.
- 구현 에이전트가 네트워크 목록에 등록되기 전에 파이프라인을 만들면 개발 담당이 비어 있다가, 개발 단계에서 그 에이전트를 고를 수 있다.

### 구현 모델 고정

`reason network serve`는 Studio의 환경 변수를 그대로 Claude Code에 넘긴다. Studio는 자신이 실행하는 Claude 세션에 다음 두 값을 지정한다.

```bash
ANTHROPIC_MODEL=claude-opus-5-5
CLAUDE_CODE_EFFORT_LEVEL=medium
```

Claude Code는 이 환경 변수를 사용자 설정보다 먼저 적용한다. `ANTHROPIC_MODEL=claude-opus-5-5`로 실행한 `claude -p`의 응답에서 사용 모델이 `claude-opus-5-5`로 기록되는 것을 이 컴퓨터(Claude Code 2.1.323)에서 확인했다. effort 적용은 Claude Code가 응답에 노출하지 않아 직접 확인하지 못했다. Codex 세션의 모델은 바꾸지 않는다.

## 개발 에이전트 실행 (Claude Code·Codex)

**개발 에이전트 실행**에서 Claude Code(Opus 5.5 · effort medium 고정) 또는 Codex를 고르고 **폴더 선택 후 실행**을 누르면 OS 폴더 선택 창이 열린다. 폴더를 고르면 폴더·브랜치·세션 이름을 보여 주는 OS 확인 창이 한 번 더 뜨고, 거기서 **실행**을 눌러야 시작된다. 두 창 모두 네이티브 계층이 띄우므로 화면(웹뷰)의 내용이 폴더를 정하거나 대신 승인할 수 없다. Studio가 실행하는 명령은 다음과 같다.

```bash
reason network serve codex --name <컴퓨터>-codex-<폴더>-<경로 해시 4자> --cwd <선택한 폴더> --non-interactive --no-color
```

알아 둘 점:

- `serve`는 Reason CLI 래퍼(`reason`, 0.2.748에서 확인)의 기능이다. 메시지 연결에 쓰는 엔진(`reason-network` 0.12.17)과는 다른 실행 파일이다.
- **실행된 에이전트는 받은 요청에 따라 그 폴더의 파일을 묻지 않고 수정한다.** `serve`는 Claude Code를 `acceptEdits` 모드로, Codex를 `workspace-write` 샌드박스로 실행하고 훅과 MCP 서버를 끈다. 도구 자체의 권한 설정을 따르지 않는다. Studio는 `--full-access`를 전달하지 않는다.
- 같은 세션 이름으로 이전에 받고 답하지 못한 요청이 있으면 `serve`가 실행 직후 그 작업부터 시작한다.
- 폴더는 OS 선택 창의 결과만 사용한다. 화면·AI·네트워크 메시지의 문자열은 실행 폴더가 될 수 없고, 선택 한 번은 실행 한 번에만 쓰인다. 실행 직전에 폴더가 선택 당시와 같은지 다시 확인한다.
- `/`, 홈 폴더와 그 상위 폴더, 홈의 숨김 폴더(`~/.ssh` 등)와 `~/Library`, 시스템 폴더(`/etc`, `/usr`, `/System`, `/Applications` 등)는 거부한다.
- **신뢰하는 프로젝트 폴더만 맡긴다.** 폴더 안의 설정과 스크립트가 에이전트 동작에 영향을 줄 수 있다.
- 세션은 4개까지 둘 수 있고(종료되어 닫지 않은 것 포함), 같은 폴더에는 에이전트 종류당 하나만 실행한다. 세션 이름은 Studio가 `[a-z0-9-]`로 만들며 경로 해시를 붙여 이름이 같은 다른 폴더와 겹치지 않게 한다.
- **중지**는 세션이 네트워크에서 내려갈 시간을 준 뒤 프로세스 그룹 전체를 종료한다. 세션이 먼저 죽고 작업자 프로세스만 남은 경우에도 **닫기**를 누르면 그 그룹을 정리한다. Studio를 종료하면 함께 중지한다. 종료된 세션은 자동으로 다시 실행하지 않는다.
- Studio가 비정상 종료되면 실행한 세션이 남는다. 터미널에서 해당 `reason network serve` 프로세스를 종료한다.
- 에이전트 CLI가 설치·로그인되어 있지 않으면 세션이 등록되어도 요청마다 실패한다. Studio는 실행 파일 유무만 확인하므로 로그인은 Agent 설정의 연결 상태에서 확인한다.
- 세션 출력에는 발신자와 메시지 발췌가 섞이므로 Studio는 보관하거나 화면에 표시하지 않는다.
- macOS·Linux만 지원한다. Windows에서는 터미널에서 직접 실행한다.

터미널에서 직접 `reason network serve …`를 실행한 세션도 같은 목록에 나타나며 동일하게 사용할 수 있다. Studio의 기존 Claude/Codex 텍스트 모델 어댑터에는 프로젝트 쓰기 권한을 추가하지 않는다.

## 단계별 작업 맡기기

디자인 → 기획 → 개발 → 음향 → 배포, 다섯 단계가 고정된 순서로 진행된다.

1. 브리프를 쓰고 단계마다 **연결된 에이전트** 중 하나를 담당으로 고른다. 비워 둔 단계는 나중에 정하거나 건너뛴다.
2. 현재 단계의 **보낼 요청 전문**이 표시된다. 확인하고 **승인하고 보내기**를 누르면 그 담당자 한 명에게 전송된다.
3. 담당자가 그 요청에 답장하면 단계가 **답장 받음**이 되고, 다음 단계 요청에 그 답장이 인용되어 다시 승인을 기다린다.
4. 배포 단계는 화면의 **배포 승인 체크**에 더해, 전송 직전에 뜨는 OS 확인 창에서 한 번 더 승인해야 보낸다. 확인 창은 네이티브 계층이 띄운다.

동작 원칙:

- 순서·받는 사람·요청문은 모두 Rust의 결정적 코드가 만든다. 모델을 쓰지 않으며 화면은 본문을 공급하지 않는다. 전송 시 네이티브 계층이 요청문을 다시 계산해, 화면에 표시했던 승인 값과 다르면 보내지 않는다. 승인 값은 요청문뿐 아니라 파이프라인·단계·받는 사람·전송 시도까지 묶은 SHA-256이므로, 담당자가 바뀌거나 전송이 불확실해진 뒤에는 이전 승인으로 보낼 수 없다. 이 값은 화면과 실제 전송 사이의 어긋남을 막는 장치이며, 화면 자체가 변조된 경우를 막는 장치는 아니다.
- **답장은 신뢰하지 않는 데이터다.** 4 KiB까지 발췌해 저장하고, 다음 요청에 `> ` 인용 블록으로만 넣는다. 저장 전에 모든 줄바꿈 형태를 `\n`으로 통일하고 제어 문자와 보이지 않는 유니코드 문자를 제거해, 답장이 인용 블록 밖의 지시처럼 보이거나 화면에 보이지 않는 내용이 섞이지 않게 한다. 답장 안의 명령·경로·플래그를 Studio가 실행하거나 해석하지 않는다. 다음 담당 에이전트가 인용문을 어떻게 다룰지는 그 에이전트에 달려 있으므로, 승인 전에 요청 전문을 확인한다.
- 배포 이외 단계의 요청문은 커밋·배포·외부 게시·결제를 실행하지 말라고 명시한다. 이것은 상대 에이전트에 대한 요청이며 강제 수단이 아니다.
- 답장은 **요청 메시지 ID에 대한 답장이면서 담당자가 보낸 것**일 때만 자동으로 연결한다. 담당자가 답장 대상을 지정하지 않고 보낸 메시지는 후보로만 표시하고 **이 답장으로 진행**을 눌러야 연결된다. 다른 요청에 대한 답장, 다른 에이전트나 다른 컴퓨터의 같은 이름 세션이 보낸 메시지는 연결하지 않는다.
- 답장 도착만으로 다음 단계가 전송되지 않는다. 전송은 매번 승인한다.
- 전송 응답이 사라지면 단계가 **전송 확인 필요**가 된다. 자동으로 다시 보내지 않으며, **보낸 것으로 보고 답장 기다리기** 또는 다시 승인해 재전송 중에서 고른다. 이 상태에서는 단계를 되돌릴 수 없고, 재전송이 전송 전에 거절되어도 **전송 확인 필요**와 중복 방지 키를 유지한다. 재전송은 같은 중복 방지 키를 쓰지만 엔진의 중복 제거는 실제 왕복으로 확인하지 않았으므로 상대에게 두 번 전달될 수 있다.
- 한 에이전트는 한 번에 한 파이프라인의 답장만 기다린다. 발신자로 답장을 구분하기 때문이다.
- 파이프라인은 `reason-network/pipelines.json`에 저장되어 앱을 다시 켜도 대기 상태가 유지된다. 최대 20개이며, 가득 차면 끝난 것부터 지운다. 진행 중인 것은 지우지 않는다.
- 답장 대기 중이고 Agent 탭이 열려 있으면 60초마다 연결을 새로고침한다. 탭이 닫혀 있으면 확인하지 않는다.
- 받은 메시지는 최근 200개만 보관하므로, 답장이 쌓인 채 오래 두면 연결 전에 목록에서 빠질 수 있다.

## 개발 작업 직접 보내기

파이프라인을 쓰지 않고 한 에이전트에게 바로 메시지를 보낼 수도 있다. **연결된 에이전트**에서 정확한 대상을 고르고, 컴퓨터·작업 폴더·브랜치 표시로 원하는 프로젝트의 에이전트인지 확인한 뒤 작업 내용을 보낸다.

보낼 메시지 예:

> 현재 toris_studio 프로젝트에서 영상 제작 화면의 오류를 조사하고, 수정 내용과 검증 결과를 이 Studio 주소로 답장해 줘. 커밋·배포·외부 게시가 필요하면 먼저 작업 내용을 알려 줘.

메시지의 전송 영수증은 상대 에이전트의 작업 완료를 의미하지 않는다. 완료 내용은 받은 답장에서 확인한다. Studio는 기본 수신자를 정하거나 전체 네트워크에 일괄 전송하지 않는다.

## 영상 제작 요청

외부 AI는 다음과 같은 **JSON 객체 하나**를 메시지 본문으로 보낸다. 코드 블록이나 앞뒤 설명을 붙이지 않는다. 화면의 **영상 요청 예시 복사** 버튼으로 같은 형식을 복사할 수 있다.

```json
{
  "schema": "toris-studio.video.v1",
  "requestId": "video-demo-001",
  "settings": {
    "topic": "Toris Studio로 쇼츠를 만드는 과정",
    "durationSec": 30,
    "aspect": "9:16",
    "style": "documentary",
    "narration": true,
    "speaker": "Sohee",
    "subtitleStyle": "shorts-bold",
    "bgm": "pulse",
    "quality": "preview",
    "engine": "",
    "visual": "stock",
    "layout": "card"
  }
}
```

위의 기본 요청은 **주제와 제작 설정**을 전달한다. 이 경우 Studio가 Agent 탭의 모델 설정으로 기획하고, 모델이 없으면 기존 기본 템플릿 결과를 사용한다.

외부 AI가 이미 작성한 대본·장면 구성은 선택 필드인 **`storyboard`**로 함께 전달한다. 화면의 **스토리보드 요청 예시 복사** 버튼에 전체 JSON 예시가 있다. 다음은 위 요청에 추가할 수 있는 30초 초안이다.

```json
{
  "title": "단월 업데이트, 달라진 세 가지",
  "story": "새로운 장비와 성장 경험을 소개하는 30초 쇼츠",
  "headline": { "top": "단월 업데이트", "bottom": "달라진 세 가지" },
  "scenes": [
    { "id": "intro", "durationSec": 10, "script": "업데이트 핵심 소개", "narration": "단월의 새로운 업데이트를 소개합니다.", "caption": "새로운 시작", "search": "moon mountain", "transition": "fade" },
    { "id": "equipment", "durationSec": 10, "script": "장비와 성장 소개", "narration": "다양한 장비를 모으며 나만의 캐릭터를 성장시켜 보세요.", "caption": "장비와 성장", "search": "fantasy sword", "transition": "cut" },
    { "id": "outro", "durationSec": 10, "script": "업데이트 확인 안내", "narration": "자세한 변경 사항은 게임에서 확인해 주세요.", "caption": "단월에서 확인하세요", "search": "mountain sunrise", "transition": "fade" }
  ]
}
```

이 객체를 최상위 요청의 `storyboard` 값에 넣는다. 받은 대본과 장면 구성은 로컬 모델로 다시 생성하지 않는다. 네이티브 계층이 검증한 원본 초안을 먼저 저장한 뒤 기존 사진 후보 검색·스토리보드 검토 화면으로 이어 준다. 출처는 Studio가 `reason-network`로 기록하며, 외부 입력으로 모델 이름·승인 상태를 지정할 수 없다.

검증 기준:

- `schema`는 `toris-studio.video.v1`.
- `requestId`는 영문·숫자·밑줄·하이픈으로 된 1–80자 문자열. 새 작업마다 새 ID를 쓴다.
- 요청 JSON은 32 KiB 이하. 중복 JSON 키와 알려지지 않은 필드를 거부한다.
- 주제 1–300자, 길이 10–120초. 비율·스타일·음성·자막·BGM·품질·장면 소스·레이아웃·엔진은 기존 `production::parse_settings`의 제한된 선택값을 사용한다.
- `storyboard`는 제목·요약·선택적인 헤드라인·스타일·2–12개 장면을 받는다. 장면 길이는 2–12초이며 합계는 기존 제작기의 목표 길이 허용 범위에 맞아야 한다. 음성을 켰으면 모든 장면에 `narration`이 필요하다.
- 장면의 `script`, `narration`, `caption`, `prompt`, `negativePrompt`, `search`, `emphasis`, `camera`, `stat`, `transition`은 기존 제작기의 제한을 따른다. 임의 필드와 중복 키는 중첩 객체에서도 거부한다.
- 명령, 파일 경로, 임의 다운로드 URL, 외부 에셋 ID, 모델 출처 위조, 승인·게시 플래그를 받지 않는다.
- 일반 대화는 메시지로 표시하고 자동으로 영상 작업을 생성하지 않는다.

### 요청을 제작으로 연결하기

1. 받은 요청에서 주제·길이·비율·장면 소스를 검토한다. 외부 스토리보드가 있으면 **받은 스토리보드**를 펼쳐 장면별 대본·나레이션을 확인한다.
2. 기본 요청은 **영상 기획 만들기**, 외부 초안은 **스토리보드 가져오기**를 누른다. Studio가 네이티브 계층에 저장된 원본 메시지를 다시 검증하고 영상 작업을 만든다.
3. **영상 제작으로 열기**를 누르면 생성된 정확한 작업을 기존 영상 화면에서 연다.
4. 스토리보드를 검토·수정하고 기존 제작 승인 버튼으로 생성을 시작한다.
5. 완성 후 기존 저장·QA·SNS 게시 초안 기능을 사용한다. 외부 게시 승인은 기존 발행 화면에서 진행한다.

수신 확인, 새로고침, 작업 열기만으로 렌더나 외부 게시를 시작하지 않는다.

### 중복 요청 처리

네트워크 팀·Studio 세션·실제 발신자·요청 ID로 요청을 식별한다. 생성한 작업의 최초 저장에 `reasonRequest` 출처 정보를 함께 기록한다.

- 같은 요청을 다시 가져오면 기존 작업 ID를 돌려준다.
- 같은 요청 ID에서 제작 설정이나 대본·스토리보드 내용이 바뀌면 오류로 알리고 새 ID를 요청한다.
- 스토리보드가 없는 기존 요청은 이전 버전과 같은 해시를 유지해 앱 업데이트 후에도 원래 작업을 찾는다.
- 앱 재시작 후에도 작업의 출처 기록으로 기존 작업을 찾는다.
- 요청 확인과 최초 저장은 하나의 잠금 구간에서 처리한다.

이는 영상 작업 중복 방지다. 네트워크가 메시지를 정확히 한 번만 전달한다는 의미는 아니다.

## 작업 상태 회신

받은 요청의 **작업 결과 확인**은 연결된 영상 작업을 읽는다. 별도의 **작업 상태 보내기** 버튼을 누르면 그 시점의 최신 상태를 다시 읽어 원래 발신자에게 답장한다.

회신 형식:

```json
{
  "schema": "toris-studio.video-result.v1",
  "requestId": "video-demo-001",
  "result": {
    "jobId": "Studio가 생성한 UUID",
    "status": "awaiting_approval",
    "stage": "storyboard",
    "title": "영상 제목",
    "hasVideo": false,
    "requiresApproval": true,
    "summary": "스토리보드 검토를 기다리고 있습니다. Studio에서 확인한 뒤 제작을 시작하세요."
  }
}
```

결과에는 필요한 상태와 요약만 포함한다. 로컬 MP4 경로, 전체 내부 로그, 설정·인증 정보는 넣지 않는다. `hasVideo`는 완료 상태·출력 정보·양수 영상 길이·QA 통과 **기록**을 확인한 값이며 새 파일 검사 결과가 아니다. 이 기능은 영상 파일 자체를 원격 AI에 업로드하지 않는다.

전송 응답이 시간 초과로 사라지면 실제 전송 여부가 불확실할 수 있다. Studio는 자동으로 재전송하지 않고 확인이 필요한 상태를 알린다.

## 네이티브 연결 구조

화면은 다음 열세 IPC만 호출한다. 모두 로컬 메인 창 권한을 확인한다.

| IPC | 동작 |
| --- | --- |
| `reason_network_refresh` | 연결·에이전트·전용 수신함 조회 및 기존 영상 작업 연결 |
| `reason_network_send` | 선택한 단일 에이전트에 사용자 메시지 전송 |
| `reason_network_accept_video` | 저장된 메시지 ID로 제작 요청 검증 및 중복 없는 기획 시작 |
| `reason_network_video_result` | 연결된 작업의 최소 상태 요약 조회 |
| `reason_network_send_result` | 실제 발신자 metadata에 연결한 상태 답장 전송 |
| `reason_pipeline_list` | 현재 네트워크의 단계 파이프라인 조회, 저장된 수신 기록으로 답장 연결 (전송 없음) |
| `reason_pipeline_create` | 브리프와 단계별 담당자로 파이프라인 생성 (전송 없음). `projectSessionId`가 있으면 그 실행 중 세션의 폴더로 앱 프로젝트 파이프라인 생성 |
| `reason_pipeline_update` | 닫힌 동작만 적용: 담당 변경·건너뛰기·되돌리기·답장 연결·보낸 것으로 간주·취소 |
| `reason_pipeline_send` | 표시한 승인 값이 일치할 때 현재 단계 요청을 담당자에게 전송. 배포 단계는 OS 확인 창에서 승인한 뒤에만 전송 |
| `reason_agent_launch` | 에이전트 종류만 받아 OS 폴더 선택 창과 OS 확인 창을 띄우고, 승인하면 `reason network serve` 시작 |
| `reason_agent_stop` | 세션 중지 또는 종료된 세션 기록 닫기 |
| `reason_agent_list` | Studio가 실행한 세션의 실행 여부와 종료 코드 |
| `reason_project_start` | 입력한 프로젝트 경로를 검사하고 OS 확인 창에서 승인하면 그 폴더에서 Claude Code(Opus 5.5 · medium) 구현 에이전트 시작. 이미 실행 중이면 재사용 |

`reason_network.rs`는 설치된 `reason-network mcp`를 shell 없이 실행한다. 진실한 MCP 클라이언트 이름 `toris-studio`와 영속적인 `REASON_NETWORK_SESSION` UUID를 사용하며, 다른 에이전트의 세션을 상속할 수 있는 환경변수를 제거한다.

일반 Reason CLI의 `network send/inbox`는 공용 `cli:terminal` 수신함을 사용하므로 이 연결에 사용하지 않는다. 전용 MCP 세션을 유지하고, 공식 엔진 소스의 로컬 JSON 규약으로 `Team`, `Who`, 전용 세션의 `Inbox(peek)`와 `Delivered`만 호출한다. MCP의 사람이 읽는 roster/inbox 텍스트에서 주소나 발신자를 추측하지 않는다. 전송은 MCP `send_message`를 사용한다.

수신 순서:

1. 현재 팀 식별자를 확인한다.
2. 전용 수신함을 읽기 전 캐시 저장 가능 여부를 확인한다.
3. `peek`로 읽고 실제 metadata·본문·요청 형식을 검증한다.
4. 임시 파일·원자적 교체·디스크 동기화로 캐시를 저장한다.
5. 저장된 메시지 ID에만 수신 확인을 보낸다.

저장 실패 시 확인 처리하지 않고 받은 메시지를 메모리에 유지한다. 저장 후 확인 전에 종료되면 메시지가 다시 전달될 수 있으며 ID로 중복 제거한다.

## 호환성과 운영 조건

- 이번 어댑터의 로컬 규약 지원 버전은 **Reason Network 엔진 0.12.17**이다. Reason CLI 래퍼의 버전과 다르다. 다른 엔진 버전은 검증되지 않은 규약으로 진행하지 않고 안내한다.
- 현재 로컬 소켓 전송과 개발 에이전트 실행은 macOS·Linux를 지원한다. Windows에서는 명시적인 미지원 상태를 반환한다.
- Reason Network의 기존 팀 설정·데이터베이스·실행 중인 로컬 daemon이 필요하다. 없으면 `setup_required` 상태와 연결 안내를 표시한다.
- 소켓 경로가 100바이트 이상인 특수한 상태 폴더는 이 어댑터에서 지원하지 않는다.
- Studio와 네트워크에 연결된 컴퓨터가 실행 중이어야 한다.
- 네트워크가 바뀌면 이전 수신함과 작업을 섞지 않고 연결을 차단한다. 팀 전환 시 캐시를 명시적으로 분리·이전하는 기능은 후속 작업이다. 캐시를 무작정 삭제하면 기존 메시지와 작업 연결을 잃을 수 있다.
- 수신 캐시는 최근 200개 메시지를 유지한다. 완료한 영상 작업의 출처 기록은 작업 자체에 남는다. 캐시에서 빠진 오래된 요청의 회신 버튼은 수신함에서 제공하지 않는다.
- 일반 에이전트 메시지의 발신자는 Reason이 `사람/세션` 형태로 전달하며 컴퓨터 정보가 없을 수 있다. 답장에는 이 원본 주소를 그대로 사용한다. 표시 이름은 목록에서 유일하게 일치할 때만 보조적으로 찾는다. 여러 컴퓨터에서 같은 세션 이름과 같은 요청 ID를 재사용하지 말고, 예를 들어 `studio-mac-dev`처럼 세션 이름을 구분한다. 네트워크가 모호한 수신자를 거부하면 임의의 컴퓨터로 재전송하지 않는다.
- 전송은 32 KiB, 수신 본문은 64 KiB 이하이며 응답·대기 시간에도 한도가 있다.
- 비밀값은 Reason의 기존 저장소가 관리한다. Studio의 수신 캐시는 세션·팀 식별자와 메시지를 담고 토큰을 복사하지 않는다.

- Rust 네트워크 계약 테스트는 가짜 로컬 daemon과 가짜 MCP 프로세스를 사용한다. 전용 식별자, 발신자 위조 방지, 저장 후 확인, 저장 실패, 중복 수신, 팀 변경, 전송 대상, 시간 초과를 검증한다.
- 영상 계약 테스트는 닫힌 설정과 중첩 스토리보드, 외부 대본 보존, 위조된 모델 출처 거부, 중복 작업 방지, 변경된 대본 충돌, 이전 해시 호환성, 최소 결과 요약을 검사한다.
- 파이프라인 계약 테스트는 순수 전이와 저장을 검사한다. 요청문 조립과 인용, 인용 블록을 벗어나려는 답장, 발췌 한도, 승인 값과 배포 승인, 다른 담당자·다른 시도로의 승인 재사용 거부, 발신자 위조 답장 거부, 후보 수동 연결, 불확실한 전송의 비재전송, 잘못된 전이 거부, 화면이 보내는 동작 형식, 저장 한도를 다룬다. 가짜 엔진으로는 승인한 요청문만 전송되고 답장이 다음 요청에 인용되는지, 중단되거나 거절된 재전송이 불확실 상태로 남는지 확인한다.
- 개발 에이전트 계약 테스트는 가짜 `reason` 셸 스크립트를 실행한다. 정확한 인자와 `--full-access` 부재, 환경 변수, 선택한 폴더 외 실행 거부, 선택 후 바뀐 폴더 거부, 시스템·설정 폴더 거부, 세션 이름 충돌 방지, 세션 한도, 프로세스 그룹 종료, 세션이 죽은 뒤 남은 작업자 정리, 앱 종료 시 정리, 자동 재시작 없음을 검사한다. 실제 에이전트는 실행하지 않으며, OS 폴더 선택 창과 확인 창 자체는 자동 테스트 범위 밖이다.
- UI 검사는 명시적인 IPC fixture다. 파이프라인은 목록의 에이전트만 배정되는지, 승인 전 전송이 없는지, 배포 체크가 필요한지, 답장이 일반 텍스트로 표시되는지를, 개발 에이전트는 화면이 에이전트 종류만 보내는지, 확인 창을 취소하면 세션이 생기지 않는지를 검사한다. 외부 대본 미리보기와 가져온 작업 열기, 작업 열기가 새 작업 생성·승인을 하지 않는지, 늦은 조회 응답이 수락된 작업 링크를 지우지 않는지, 사용자 동작 전 전송되지 않는지를 검사한다.
- 읽기 진단 예제는 실제 설치된 엔진과 전용 세션을 확인하되 메시지를 보내거나 수신 확인하지 않는다. 모델·렌더·외부 계정 게시 검증과는 별개다.

- 앱 프로젝트 계약 테스트는 4단계 순서와 단계별 요청문, 프로젝트 현황 인용, 개발 담당 고정·건너뛰기 금지, 다른 파이프라인 단계 거부, 전송 한도, 저장 형식(이전 기록 호환), 현황 수집(숨김·`node_modules`·심볼릭 링크 제외, README 정리), 입력 경로 해석과 거부, Claude 세션의 모델·effort 환경 변수를 다룬다. UI 검사는 화면이 입력 경로와 세션 ID만 보내는지, 확인 창 취소 시 아무것도 시작하지 않는지, Muse·OpenAI Dots 추천, 개발 담당 고정을 확인한다.

실제 외부 AI와의 왕복, 실제 `reason network serve` 세션 실행, 실제 영상 렌더, 실제 YouTube 게시는 각각 별도로 실행한 증거가 있어야 성공했다고 보고한다. 이 문서 작성 시점에 단계 파이프라인과 개발 에이전트 실행은 실제 에이전트로 왕복한 증거가 없다.
